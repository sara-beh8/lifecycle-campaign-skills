# lifecycle-campaign-skills

**A lifecycle campaign build pipeline as AI skills** — naming & tracking → design → segment → copy → HTML → QA — so campaigns are built by a governed process instead of heroics, and old campaigns can generate their own successors.

## The story

I revised a lifecycle program of many concurrent campaigns. The estate I inherited was typical: campaigns over a year old, outdated product references, no renewal process. Rebuilding each one by hand doesn't scale — so I codified the *process* of building a campaign as a set of AI skills (originally [Claude Code](https://claude.com/claude-code) skills), each producing a reviewable artifact.

The result is a loop, not a pile: **audit an old campaign → pull current product context → regenerate its successor → QA against guardrails → log the renewal**. The same rails powered an automated AI outbound layer ([`ai-outbound-engine`](https://github.com/sara-beh8/ai-outbound-engine)) and let the program ship an A/B test every two weeks. Full case study: [sara-beh8.github.io](https://sara-beh8.github.io)

Everything here is **generalized with a fictional company and synthetic data** — the architecture is real, the configs are examples.

## The pipeline

| Stage | Skill | Input → Output |
|---|---|---|
| 0 | [`skills/naming-and-tracking`](skills/naming-and-tracking/SKILL.md) | Brief one-liner + [`config/naming-utm.yaml`](config/naming-utm.yaml) → campaign name, registry slug, full UTM set. **Tracking is generated before anything is built** — the slug is the dashboard's join key, so the campaign is measurable on day one |
| 1 | [`skills/campaign-design`](skills/campaign-design/SKILL.md) | Business goal → campaign brief (audience, entry/exit, success metrics, flow sketch) |
| 2 | [`skills/segment-spec`](skills/segment-spec/SKILL.md) | Brief → segment definition (baseline + excludes + campaign logic, as boolean spec) |
| 3 | 🔒 `skills/email-copy` | Brief + brand config + product context → email copy with real proof points — links may only carry UTMs enumerated in stage 0 |
| 4 | 🔒 `skills/html-build` | Approved copy + email template → production HTML with personalization fallbacks — only stage-0 links allowed, plain-text version generated alongside |
| 5 | 🔒 `skills/qa-checklist` | Built campaign → structured QA verdict (links + UTMs diffed against stage 0, rendering, segment sanity, guardrails) |

Downstream, every campaign lands in the attribution dashboard automatically because `utm_campaign` = registry slug: see [`growth-dashboard-spec`](https://github.com/sara-beh8/growth-dashboard-spec) for the measurement layer this feeds.

Each skill is a `SKILL.md` instruction file (with name/description frontmatter, so it installs directly as a Claude skill) that a capable LLM agent can execute; artifacts are files, so every step is diffable and reviewable before anything touches the sending tool.

## Design principles

1. **Product context is an input, not a memory.** Copy generation must pull *current* features/roadmap — this is what keeps renewed campaigns from repeating year-old claims.
2. **Guardrails over trust.** URL allowlists and product-name dictionaries in the copy skill — because the first version of my AI pipeline hallucinated both, failed QA on rendering, and taught me to ship the guardrails before the feature.
3. **Human metrics only.** QA and reporting read human opens/clicks, never machine-inflated totals.
4. **Everything lands in a registry.** See the companion repo: [`lifecycle-ops-standards`](https://github.com/sara-beh8/lifecycle-ops-standards).
